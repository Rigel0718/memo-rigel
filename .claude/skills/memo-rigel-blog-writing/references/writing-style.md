# 공통 문체 및 편집 기준

이 문서는 **모든 글에 적용되는 표현·가독성 원칙**을 정한다. 두 Writing Mode의 전개 절차는 각 전용 reference를 따른다. 기존 Agent 원고 두 편과 HITL 글쓰기 피드백, GIL 원고를 참고했으며 예시 원고의 목차는 템플릿이 아니다.

## 문장과 전개
- 자연스러운 한국어 기술 글을 쓴다. 필요한 영문 기술 용어와 코드 식별자는 정확하게 유지한다.
- 글 첫머리에서 상투적인 선언이나 결론 요약을 반복하지 않는다. 질문, 이전 에피소드의 맥락, 현상, 코드 등 **그 주제에 적절한 도입**을 택한다.
- 문장·문단 사이 인과관계를 명확히 하고, 초반부의 흐름도 후반부만큼 세심하게 검토한다. 매 문장을 한 줄 문단으로 강제하지 않는다.
- 소제목은 해당 절이 담당하는 질문·개념·설명의 목적을 드러낸다. 아직 논증하지 않은 결론을 문맥 없이 먼저 선언하지 않는다.
- 기술 설명에 필요할 때만 표, 코드, 텍스트 다이어그램을 쓴다. 같은 도식을 약간 바꾸어 여러 번 되풀이하지 않는다.
- 개념을 설명할 때는 개념 이름을 우선 쓰고 실제 함수명·변수명은 구현을 구체적으로 다룰 때 등장시킨다.
- 적절한 예제는 추상적 내용을 돕지만, **예제에 맞춰 내용과 글의 구조를 억지로 끌고 가지 않는다**.

## 근거와 목소리
- 객관적으로 확인할 기술 사실, 사용자의 관찰, 개인적 해석, 가정·가능성을 구분한다.
- 사용자가 제공하지 않은 사건·고민·성공·실패를 1인칭 경험으로 꾸미지 않는다.
- 실제 구현 당시 선택 이유와 나중에 복습하면서 발견한 설계 의미를 혼합하지 않는다.
- 사용자의 강조점이 무엇인지 글에 반영하되 한 글에서 중요했던 철학을 다른 주제의 고정 결론으로 일반화하지 않는다.
- 범위와 한계를 분명히 하되 필요 이상으로 극단적인 반례나 방어적인 단서를 늘어놓지 않는다.

## 중복과 가독성
- 앞에서 정의한 내용을 뒤에서 재활용할 때는 새로 얻는 이해가 있는지 확인한다. 단순 반복이라면 삭제·통합한다.
- 코드와 도식이 긴 경우 무엇을 보여 주는지, 독자가 무엇을 확인해야 하는지 먼저 설명한다.
- Python 기술 글에서는 선행 에피소드와 연결하되 이전 글 전체를 다시 설명하지 않는다.
- 원고에서 길고 반복적인 번호 절·`---`·텍스트 화살표가 관찰되더라도 그대로 모방하지 않는다. 이것들은 필요하면 줄이거나 한 도식으로 통합할 편집 대상이다.
- 결론은 **이번 글의 목적**에 맞춘다. 개인 관점에 도달할 수도 있고, 개념의 작동 원리를 정리할 수도 있다. 매번 교훈이나 질문으로 끝내지 않는다.

## 수정 작업
- 요청받은 표현·단락만 수정할 때는 다른 합의 부분을 함부로 바꾸지 않는다.
- 논점이나 설명 정확성이 바뀌면 관련된 도입·절·결론까지 영향 범위를 확인한다.
- 수정 결과를 별도 설명하는 것보다 필요할 때 바뀐 원고를 명확하게 보여준다.
