# 사유형 기술 에세이 — Perspective-driven Writing

## 사용 시점과 목표
Agent에 대한 고찰·Agent 설계 노트처럼 사용자가 실제 구현, 학습, 질문을 통해 얻은 **관점과 판단**을 글로 발전시키고 싶을 때 적용한다. 사실 설명도 중요하지만 메시지의 소유자는 사용자다.

## 대화 흐름 (고정 단계 아님)
1. 주제, 실제 경험·자료, 사용자에게 중요한 질문을 파악한다. **기술 소재**와 **이 글의 메시지**를 구분한다.
2. 사용자가 아직 중심 메시지를 정하지 못했다면 하나의 핵심 질문이나 구체적 대안을 제시하고 함께 판단을 정리한다. 사용자가 이미 충분한 내용을 말했으면 곧바로 개요 또는 초안으로 이동한다.
3. 사용자의 초기 생각에 필요한 반례·대안·비용을 검토한다. 반론을 위한 반론이나 과장된 위험 시나리오로 주제를 확대하지 않는다.
4. 어떤 사실이 실제 구현 당시 결정이었는지, 어떤 생각은 복습에서 뒤늦게 알게 된 것인지 확인한다. 결과에 맞춰 의도와 경험을 소급해 만들지 않는다.
5. 사용자와 합의한 중심 논점으로 **이번 글만의 흐름**을 설계한다. 질문에서 시작할 수도 있고 구현, 비유, 관찰에서 시작할 수도 있다.
6. 초안과 수정에서는 기술적 사실이 정확하고 사용자의 의도가 왜곡되지 않았는지 반복 확인한다. 사용자 관점과 문서·공식 정의는 구분한다.

## HITL 글쓰기 테스트에서 배운 것
- Issue#3 기술 설명 자체보다 'HITL 추가 시 Agent Loop의 기존 책임을 유지할 것인가'가 실제 중심 논점이었다.
- `PendingApproval`, history 기반 Resume, Orchestration Loop는 그 논점을 뒷받침하는 구현 근거로 설명했다.
- 이전 Permission/Approval 원고의 `write_file` 도입을 복제하자 부자연스러웠고, 기본 Agent Loop → 새 요구사항으로 도입을 변경했다.
- 책임 분리 관점은 그 글의 메시지이므로 **다른 글에 자동으로 삽입하지 않는다**.

## 결과 점검
- 사용자가 실제로 믿고 전달하려는 주장인가? 사용자와 합의하지 않은 '철학'을 덧씌우지 않았는가?
- 절의 설명이 핵심 메시지로 모이는가? 글 끝에서 구현 요약만 반복하지 않는가?
- 범위를 명확히 하면서 다른 상황에서 판단이 달라질 가능성을 남기는가?
