# Astro 발행 절차

사용자가 원고를 승인하고 저장을 요청했을 때만 이 절차를 따른다. 각 단계에서 확인한 사실을 근거로 삼고, 저장소 구조나 스키마를 추측으로 채우지 않는다.

## 1. 저장소 구조 확인
- Content Collection 설정 파일을 찾는다. 보통 `src/content.config.ts`(Astro 5 이후) 또는 `src/content/config.ts`에 있다.
- 블로그 컬렉션의 스키마(필수·선택 필드, 타입, 기본값)를 읽는다.
- 글이 저장되는 디렉터리와 파일·폴더 이름 규칙을 기존 글에서 확인한다. (예: `src/content/blog/<series>/<slug>.md`, 번호 접두사 여부)
- 같은 시리즈의 최근 글 한두 편의 frontmatter를 읽어 실제로 쓰는 필드와 값의 형식을 확인한다.

## 2. Frontmatter 작성
- 스키마에 정의된 필드만 쓴다. 스키마에 없는 필드를 만들지 않는다.
- 필수 필드는 모두 채운다. 원고와 대화에서 값을 알 수 없는 필드(예: 태그, 요약, 대표 이미지)는 지어내지 말고 사용자에게 제안 값을 보여주고 확인받는다.
- 날짜는 기존 글의 형식을 따르고, 시간대는 Asia/Seoul 기준으로 한다.
- 시리즈·순서 필드가 있으면 앞 에피소드와 번호가 이어지는지 확인한다.
- 스키마에 `draft` 같은 공개 여부 필드가 있으면 사용자에게 값을 확인한다.

## 3. 파일 저장
- 저장할 경로와 파일명, frontmatter를 먼저 보여주고 확인받는다.
- 같은 경로에 파일이 있으면 덮어쓰지 않고 사용자에게 알린다. 기존 글 수정 요청이면 바뀌는 부분만 수정한다.
- 이미지나 첨부 자료가 있으면 기존 글이 쓰는 위치와 참조 방식(상대 경로, `public/` 등)을 따른다.
- 본문은 대화에서 합의한 통합 원고를 그대로 쓴다. 저장하면서 문장을 다시 고치지 않는다.

## 4. 빌드 확인
- lockfile로 패키지 매니저를 판단한다. (`pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn, `package-lock.json` → npm, `bun.lockb`/`bun.lock` → bun)
- `package.json`의 scripts를 확인하고 빌드 스크립트를 실행한다. `astro check` 스크립트가 있으면 함께 실행한다.
- 스키마 검증 오류, 깨진 링크·이미지 경로, Markdown 렌더링 문제를 확인한다.
- 오류가 이번 글 때문이면 원인과 수정안을 보여주고 승인 후 고친다. 이번 글과 무관한 기존 오류는 고치지 않고 보고만 한다.
- 빌드를 실행하지 못했거나 일부만 확인했다면 그 사실을 그대로 보고한다.

## 5. Git
- 변경 파일 목록과 diff 요약을 보여준다.
- 커밋은 사용자가 요청할 때만 한다. 커밋 메시지는 `git log`로 확인한 기존 메시지 규칙을 따른다.
- 사용자가 지정하지 않으면 현재 브랜치에서 작업하고, 새 브랜치를 만들지 않는다.
- push와 배포는 사용자가 명시적으로 요청할 때만 한다.
