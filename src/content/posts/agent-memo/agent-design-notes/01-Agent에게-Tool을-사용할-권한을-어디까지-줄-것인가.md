Agent에게 `write_file`이라는 Tool을 제공했다고 생각해 보자.

Agent는 새로운 파일을 생성할 수도 있고, 기존 파일의 내용을 수정할 수도 있다.

그렇다면 Agent에게 `write_file`을 사용할 권한이 있다는 것은, 그 Tool로 수행하는 모든 행동을 허용한다는 의미일까?

`tool-mcp-skill-lab` 프로젝트에서 처음 Permission을 구현할 때는 Tool 이름을 기준으로 사용 권한을 부여했다.

어떤 사용자가 `read_file`, `write_file`, `run_command`와 같은 Tool을 사용할 수 있는지 판단하는 단순한 구조였다.

그런데 Approval을 추가하면서 조금 다른 문제가 생겼다.

**Tool을 사용할 자격이 있는 것과, 그 Tool이 수행하려는 행동을 그대로 실행해도 되는 것은 다르지 않을까?**

## Permission과 Approval은 무엇이 다른가?

사용자 A에게 `write_file` Permission이 있다고 가정하자.

Agent가 다음 두 작업을 요청했다.

```
# Case A: 새로운 파일 생성
write_file(path="new_file.py", content="hello")

# Case B: 기존 파일 덮어쓰기
write_file(path="existing_file.py", content="hello")
```

두 작업 모두 동일한 `write_file` Tool을 사용한다.

Permission만 확인한다면 두 작업 모두 허용된다. 사용자 A에게 `write_file`을 사용할 권한이 있기 때문이다.

하지만 두 작업이 기존 상태에 미치는 영향은 다르다.

새로운 파일을 생성하는 작업은 기존 파일의 내용을 직접 변경하지 않는다. 반면 기존 파일을 덮어쓰면 그 안에 있던 내용이 사라질 수 있다.

나는 이 둘을 구분할 필요가 있다고 생각했다.

사용자에게 파일을 쓸 수 있는 권한이 있더라도, 기존 파일의 내용을 잃을 수 있는 작업이라면 한 번 더 확인하는 편이 적절하다고 판단했다.

그래서 Permission과 Approval을 분리했다.

- **Permission:** 사용자가 해당 Tool을 사용할 권한이 있는가?
    
- **Approval:** 이번 Tool Call을 사용자 승인 없이 자동 실행해도 되는가?
    

Permission은 사용자와 Tool의 관계를 판단한다. Approval은 Permission을 통과한 개별 Tool Call의 실행 여부를 판단한다.

Permission이 없는 사용자는 Approval을 받더라도 해당 Tool을 사용할 수 없다. 반대로 Permission이 있는 사용자라도 모든 Tool Call을 자동으로 실행할 수 있는 것은 아니다.

이번 구현에서는 Permission을 먼저 확인하고, 허용된 Tool Call에 대해 Approval 필요 여부를 판단하도록 설계했다.

```
Agent
  │
  ▼
Tool Call
  │
  ▼
Permission
  │
  ├─ Denied ──▶ 실행 거부
  │
  ▼
Approval Policy
  │
  ├─ 승인 필요 ──▶ 자동 실행 차단
  │
  ▼
Tool Execution
```

여기서 Approval은 모든 호출에 대해 사용자 승인을 요청한다는 의미가 아니다.

**사용자 개입 없이 실행할 수 있는 호출과, 실행 전에 확인이 필요한 호출을 구분하는 과정**이다.

그렇다면 Permission 자체를 더 세밀하게 설계하면 Approval 없이도 해결할 수 있지 않을까?

이번 프로젝트에서는 Permission을 Tool 이름 기준으로 관리했지만, 실제 Application에서는 사용자의 Role이나 접근하려는 Resource에 따라 권한을 판단해야 할 수도 있다.

그런 요구사항이 있다면 Permission 자체를 더 세밀하게 설계하는 편이 적절하다.

하지만 Permission을 세분화하더라도 허용된 영역에서 수행하려는 개별 행동의 위험은 별도로 판단할 수 있다.

가령 특정 프로젝트의 파일을 수정할 권한이 있는 사용자라도, 기존 설정 파일을 덮어쓰는 작업에는 추가적인 확인을 요구할 수 있다.

두 정책이 판단하려는 대상이 다르기 때문이다.

이번 프로젝트에서는 아직 복잡한 Role이나 Resource 단위의 Permission이 필요하지 않았다. 그래서 Tool 이름을 기준으로 사용 자격을 판단하고, 개별 행동의 자동 실행 여부는 Approval에서 다루기로 했다.

## 같은 Tool이라도 행동의 위험은 다르다

Permission을 Tool 이름 기준으로 관리했다면, Approval도 Tool 이름만으로 판단할 수 있지 않을까?

예를 들어 `write_file`을 항상 Approval 대상으로 지정하는 방법도 있다.

구현은 단순해진다. 파일을 쓰려는 모든 요청에 대해 사용자 확인을 요구하면 되기 때문이다.

하지만 이렇게 하면 새로운 파일을 생성하는 작업까지 매번 승인을 받아야 한다.

반대로 `write_file`을 항상 자동 실행하도록 허용하면 기존 파일을 덮어쓰는 작업도 별도의 확인 없이 실행된다.

결국 같은 Tool이라도 어떤 행동을 수행하려는지에 따라 다르게 판단할 필요가 있었다.

이번 구현에서는 `write_file`이 전달받은 경로에 파일이 이미 존재하는지 확인하도록 했다.

- 존재하지 않는 파일이라면 자동 실행한다.
    
- 이미 존재하는 파일이라면 Approval을 요구한다.
    

기존 파일의 내용을 보호하는 것을 판단 기준으로 삼은 것이다.

이 부분을 복습하면서 처음에는 멱등성(Idempotency)을 떠올렸다.

같은 Tool이라도 arguments에 따라 멱등적인 작업과 그렇지 않은 작업이 달라질 수 있으므로, 그 차이를 기준으로 Approval을 판단한다고 생각했다.

그런데 멱등성과 기존 상태를 변경할 위험은 다른 개념이었다.

예를 들어 기존 파일에 매번 동일한 내용을 덮어쓰는 작업을 생각해 보자.

같은 작업을 반복해도 최종 파일 내용이 같다면 멱등적인 작업일 수 있다. 하지만 기존 파일의 내용이 변경된다는 사실은 달라지지 않는다.

이번 Approval에서 판단하려는 것은 반복 실행의 결과가 아니라, **기존 파일의 내용을 잃을 수 있는가**였다.

이 차이를 이해하고 나니 Approval이 Tool 이름만이 아니라 개별 Tool Call의 arguments와 실행 환경을 확인해야 하는 이유도 더 분명해졌다.

물론 새로운 파일을 생성하는 작업이라고 해서 항상 안전한 것은 아니다.

새로운 설정 파일이나 실행 스크립트를 생성하는 것만으로도 프로그램의 동작에 영향을 줄 수 있다.

그렇다면 이런 부작용까지 모두 분석해야 할까?

이번 프로젝트에서는 그렇게 구현하지 않았다.

Permission과 Approval을 통해 Tool 실행을 통제하는 구조를 이해하는 것이 첫 번째 목표였기 때문이다.

모든 부작용을 분석하기보다는 기존 파일의 내용을 덮어쓰는 작업을 Approval 대상으로 정했다.

이 기준이 모든 Application에서 충분하다는 의미는 아니다. 실제로 보호해야 하는 대상과 요구사항이 달라진다면 Approval 판단 기준도 달라져야 할 것이다.

## 명시적으로 허용한 행동만 자동 실행하기

`write_file`은 파일의 존재 여부를 기준으로 자동 실행 여부를 구분할 수 있었다.

하지만 `run_command`는 조금 더 복잡하다.

같은 Tool이라도 어떤 명령을 전달하느냐에 따라 수행하는 행동이 완전히 달라지기 때문이다.

예를 들어 다음 명령을 생각해 보자.

```
git status
git push
pytest
```

세 명령 모두 `run_command`를 통해 실행할 수 있지만, 시스템에 미치는 영향은 다르다.

이번 프로젝트에서는 다음과 같은 Allowlist를 사용했다.

```
AUTO_APPROVED_COMMANDS = {
    "git": {"status", "diff", "log"},
    "pytest": None,
}
```

`git status`, `git diff`, `git log`, `pytest`는 자동 실행을 허용하고, 그 외의 명령은 Approval 대상으로 분류했다.

여기에는 두 가지 접근 방식이 있다.

하나는 위험하다고 판단한 명령만 제한하는 Denylist 방식이다. 다른 하나는 명시적으로 허용한 명령만 자동 실행하는 Allowlist 방식이다.

나는 이번 프로젝트에서 Allowlist를 선택했다.

우선 학습 목적의 프로젝트였기 때문에 자동 실행할 수 있는 범위를 명확하게 제한하는 것이 적절하다고 생각했다.

Permission과 Approval의 역할을 이해하는 것이 우선이었고, 다양한 명령을 자동으로 실행하도록 허용할 필요는 없었다.

복습하면서는 이 선택의 또 다른 장점도 확인할 수 있었다.

Agent가 생성할 수 있는 모든 명령과 그 부작용을 미리 파악하기는 어렵다.

예를 들어 다음과 같은 명령을 생각해 보자.

```
python generate_report.py
```

명령어 자체만으로는 스크립트 내부에서 어떤 파일을 생성하거나 수정하는지 알 수 없다.

위험한 명령만 차단하는 방식이라면, 미처 예상하지 못한 행동이 자동으로 실행될 수도 있다.

반면 Allowlist를 사용하면 명시적으로 허용하지 않은 명령은 사용자 확인을 거치도록 제한할 수 있다.

다만 **Allowlist에 포함되어 있다는 것이 그 명령의 모든 부작용을 검증했다는 의미는 아니다.**

이번 프로젝트에서도 명령어 내부의 동작을 분석하거나 간접적인 부작용까지 확인하는 기능은 구현하지 않았다.

자동 실행할 수 있는 범위를 명시적으로 제한한 것이다.

이처럼 허용되지 않은 호출을 기본적으로 자동 실행하지 않는 방식을 Fail-closed라고 부를 수 있다.

Permission에서도 비슷한 방식을 사용했다. 새로운 Tool이 추가되었을 때 Permission 설정이 누락되었다는 이유로 사용자가 의도하지 않은 권한을 얻지 않도록 하기 위해서다.

하지만 기본적으로 제한하는 방식이 언제나 최선인 것은 아니다.

## 통제를 강화할수록 발생하는 비용

Allowlist를 사용하면 Application이 자동 실행을 허용하는 범위를 명확하게 관리할 수 있다.

예상하지 못한 명령이 자동 실행될 가능성도 줄일 수 있다.

하지만 그만큼 감수해야 하는 비용이 있다.

먼저 정책을 유지보수해야 한다.

Application의 목적이 달라지거나 Tool의 사용 범위가 넓어진다면 Allowlist도 함께 수정해야 한다.

또 Agent가 문제 해결에 적절한 행동을 선택했더라도 정책에서 허용하지 않았다면 Approval이 필요하다.

Agent의 판단이 잘못된 것은 아니지만, Application이 그 행동의 자동 실행을 허용하지 않은 것이다.

이런 상황이 반복되면 사용자 개입이 늘어나고 Agent가 자율적으로 수행할 수 있는 작업의 범위도 제한된다.

Permission에서도 비슷한 고민이 있었다.

이번 프로젝트에서는 명시적으로 허용하지 않은 사용자와 Tool을 기본적으로 거부하도록 설계했다.

하지만 모든 Agent가 동일한 수준의 통제를 필요로 하는 것은 아니다.

상대적으로 위험이 작은 정보를 조회하는 Agent와 중요한 데이터를 변경하는 Agent를 같은 기준으로 관리해야 할까?

엄격한 Permission을 적용하면 의도하지 않은 실행을 줄일 수 있다. 반대로 모든 작업에 세밀한 정책을 적용하면 그 정책을 관리하는 비용과 시스템의 복잡성도 증가한다.

Approval 역시 마찬가지다.

사용자 확인을 늘리면 특정 작업을 실행하기 전에 개입할 기회가 생긴다. 하지만 확인이 너무 잦아지면 Agent를 사용하는 효율이 떨어질 수도 있다.

결국 잘못 허용했을 때 발생하는 비용뿐 아니라, **잘못 차단했을 때 발생하는 비용**도 함께 고려할 필요가 있다.

여기서 한 가지 구분해야 할 점도 있다.

이번 Permission에서 선택한 Fail-closed는 주로 **명시적인 권한 설정이 없는 대상을 기본적으로 거부한다**는 의미다.

정책 시스템 자체에 장애가 발생했을 때 반드시 전체 서비스를 중단해야 한다는 결정까지 내린 것은 아니다.

어떤 상황에서 기본적으로 허용하거나 거부할지는 해당 정책이 무엇을 보호하려는지에 따라 별도로 판단해야 한다.

## 어디까지 허용하는 것이 적절할까?

이번 프로젝트에서는 Tool 이름을 기준으로 Permission을 부여하고, 개별 Tool Call의 자동 실행 여부를 Approval로 판단했다.

기존 파일을 덮어쓰는 작업에는 Approval을 요구했고, `run_command`는 명시적으로 허용한 명령만 자동 실행하도록 제한했다.

모든 Tool 실행의 위험을 분석하려는 것은 아니었다. Permission과 Approval이 서로 다른 문제를 해결한다는 것을 이해하고, 실제 실행 흐름에 적용해 보는 것이 우선이었다.

복습하면서는 이러한 설계가 가진 한계도 생각해 볼 수 있었다.

Permission이 너무 넓다면 권한 자체를 더 세밀하게 설계해야 할 수 있고, Approval을 엄격하게 적용할수록 사용자 개입과 정책 관리 비용이 증가할 수 있다.

결국 **Agent에게 어디까지 행동을 허용할 것인지는 하나의 정책만으로 결정하기 어려운 문제**인 것 같다.

이번에는 학습 목적과 구현 범위를 고려해 단순한 Permission 모델과 제한적인 자동 실행 정책을 선택했다.

앞으로 다른 Agent를 설계한다면, 그 Agent가 수행할 작업과 보호해야 할 대상, 그리고 통제로 인해 발생하는 비용을 함께 고려해 허용 범위를 결정해야 할 것이다.
