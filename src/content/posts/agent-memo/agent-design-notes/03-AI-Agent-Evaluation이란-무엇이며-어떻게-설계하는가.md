AI Agent를 구현했다고 가정해 보자.

Agent는 사용자의 요청을 해석하고, 필요한 Tool을 선택하며, 실행 결과를 바탕으로 작업을 수행한다. 단순히 답변을 생성하는 것을 넘어 외부 데이터를 조회하거나 시스템의 상태를 변경할 수도 있다.

그렇다면 Agent가 정상적으로 작동하고 있다는 사실을 어떻게 검증할 수 있을까?

최종 답변이 정확하다면 성공했다고 판단해도 될까? 올바른 답변을 생성했지만 잘못된 Tool을 사용했다면 어떻게 평가해야 할까? 같은 요청을 여러 번 실행했을 때 결과가 달라진다면 시스템의 신뢰성을 어떻게 판단할 수 있을까?

이러한 질문에 체계적으로 답하기 위한 방법이 **Agent Evaluation**이다.

Evaluation은 단순히 Agent에 점수를 부여하는 작업이 아니다. 무엇을 성공으로 판단할지 정의하고, 일정한 기준으로 시스템을 검증하며, 결과를 바탕으로 개선과 설계 판단의 근거를 마련하는 과정이다.

## 1. Agent Evaluation이란 무엇인가?

Evaluation은 모델이나 AI 시스템이 주어진 작업을 얼마나 잘 수행하는지 정의된 기준에 따라 측정하고 평가하는 과정이다.

OpenAI의 *Evaluation Best Practices*에서는 Evaluation을 생성형 AI 시스템의 가변적인 출력에도 불구하고 정확성, 성능, 신뢰성을 검증하기 위한 구조화된 테스트로 설명한다.

일반적인 소프트웨어에서는 입력에 대해 기대하는 결과를 비교적 명확하게 정의할 수 있다.

예를 들어 두 정수를 더하는 함수라면 다음과 같이 테스트할 수 있다.

```python
assert add(2, 3) == 5
```

하지만 Agent는 일반적인 결정적 함수와 다른 특성을 가진다.

Agent는 LLM의 판단에 따라 Tool을 선택하거나 실행 경로를 결정할 수 있으며, 같은 요청을 입력하더라도 서로 다른 실행 과정과 결과가 나타날 수 있다.

그렇다고 실행 과정이 달라졌다는 이유만으로 실패했다고 판단할 수는 없다.

예를 들어 고객의 구독 상태를 확인하는 Agent가 있다고 가정하자.

첫 번째 실행에서는 고객 정보를 먼저 조회하고 구독 정보를 확인했지만, 두 번째 실행에서는 이미 제공된 고객 정보를 활용하여 바로 구독 정보를 조회할 수 있다.

두 실행이 모두 올바른 고객의 구독 상태를 확인했다면 서로 다른 실행 경로가 반드시 문제가 되는 것은 아니다.

따라서 Agent Evaluation에서는 단순히 출력이나 실행 순서가 기대값과 일치하는지 확인하는 것에서 나아가, **주어진 작업의 목표를 달성했는지, 필요한 제약 조건을 준수했는지, 실행 과정이 적절했는지 평가해야 한다.**

### LLM Evaluation과 Agent Evaluation

Agent Evaluation을 이해하기 위해서는 LLM Evaluation과의 관계를 알아둘 필요가 있다.

**LLM Evaluation**은 모델 자체 또는 LLM 기반 애플리케이션의 출력과 성능을 평가하는 개념이다.

질문에 대한 정확성, 문서 요약의 충실도, 지시 사항 준수, 근거 없는 주장 등이 대표적인 평가 대상이다.

반면 **Agent Evaluation**에서는 모델의 출력뿐 아니라 목표 달성을 위한 실행 과정과 실제 환경의 상태까지 평가할 수 있다.

예를 들어 고객의 환불을 처리하는 Agent를 생각해 보자.

Agent가 "환불이 완료되었습니다."라고 답변했다고 해서 작업이 성공했다고 판단할 수는 없다.

실제로 환불이 처리되었는지, 올바른 고객의 요청을 처리했는지, 필요한 권한과 정책을 준수했는지도 확인해야 한다.

| 구분 | 주요 평가 대상 |
|---|---|
| LLM 응답 평가 | 정확성, 관련성, 충실도, 지시 이행 |
| Agent 실행 평가 | 목표 달성, Tool 사용, 실행 과정, 상태 변경, 안전성 |

두 개념이 완전히 분리되는 것은 아니다.

LLM Evaluation을 넓은 의미로 사용하면 LLM 기반 애플리케이션 전체의 평가를 포함할 수 있다. Agent Evaluation은 여기에 다단계 실행과 Tool 사용, 환경 상태 변화 등을 고려한 평가 영역이라고 이해할 수 있다.

## 2. Agent의 무엇을 평가해야 하는가?

Evaluation을 설계할 때 가장 먼저 고민해야 할 것은 평가 지표가 아니라 **평가하려는 목적**이다.

같은 Agent라도 수행하는 작업에 따라 중요한 평가 기준이 달라진다.

문서 검색 Agent라면 필요한 정보를 정확하게 검색하고 근거를 제시하는지가 중요할 수 있다.

고객 지원 Agent라면 문제의 원인을 정확하게 파악하고 정책에 맞는 해결 방법을 제시해야 한다.

시스템을 직접 조작하는 Agent라면 실제 작업 수행 여부와 권한 및 안전 조건의 준수가 더욱 중요해질 수 있다.

이러한 평가 대상을 이해하기 위해 크게 세 가지 관점으로 구분해 볼 수 있다.

### 2.1 Outcome — 무엇을 달성했는가?

Outcome은 Agent가 실행 결과로 무엇을 달성했는지에 관한 평가다.

대표적으로 다음과 같은 항목을 평가할 수 있다.

- **Correctness**: 결과가 사실 또는 기대 조건에 부합하는가?
- **Task Success**: 주어진 작업의 목표를 달성했는가?
- **Groundedness**: 생성된 주장이 제공된 정보나 근거로 뒷받침되는가?
- **Safety**: 정책이나 안전 조건을 위반하지 않았는가?

예를 들어 고객 지원 Agent가 팀원 초대 실패 원인을 진단하는 상황을 생각해 보자.

올바른 원인을 식별했는지, 실제 고객 데이터와 정책을 근거로 설명했는지, 잘못된 해결 방법을 제시하지 않았는지가 Outcome 평가에 해당한다.

여기서 중요한 것은 **Agent가 성공했다고 주장한 것과 실제로 성공한 것은 다를 수 있다는 사실**이다.

특히 실제 시스템의 상태를 변경하는 Agent라면 최종 답변뿐 아니라 작업 이후의 상태까지 검증해야 한다.

### 2.2 Process — 어떻게 달성했는가?

Process는 Agent가 결과에 도달하기까지의 실행 과정을 평가한다.

Agent는 여러 단계에 걸쳐 Tool을 호출하거나 중간 결과를 해석하면서 다음 행동을 결정할 수 있다.

이때 다음과 같은 내용을 확인할 수 있다.

- 적절한 Tool을 선택했는가?
- 필요한 정보에 정상적으로 접근했는가?
- Tool 호출에 올바른 인자를 전달했는가?
- 오류 상황을 적절하게 처리했는가?
- 실행 중 보안 정책이나 제약 조건을 위반하지 않았는가?

다만 좋은 실행 과정이 반드시 하나의 정해진 순서를 의미하지는 않는다.

Agent는 동일한 목표를 여러 방법으로 달성할 수 있다. 따라서 특별한 이유 없이 Tool 호출 순서를 고정하여 평가하면 정상적인 해결 방법까지 실패로 처리할 수 있다.

정확한 실행 순서가 필수적인 작업이라면 이를 검증해야 하지만, 그렇지 않다면 목표 달성과 필수적인 제약 조건 준수에 집중하는 편이 적절하다.

### 2.3 Efficiency — 얼마나 효율적으로 달성했는가?

Efficiency는 Agent가 작업을 수행하는 데 사용한 시간과 자원을 평가한다.

대표적인 지표는 다음과 같다.

| 지표 | 의미 |
|---|---|
| Latency | 요청부터 응답 또는 작업 완료까지 걸린 시간 |
| Token Usage | LLM 호출에 사용한 입력 및 출력 토큰 |
| LLM Calls | 모델을 호출한 횟수 |
| Tool Calls | 외부 Tool을 호출한 횟수 |
| Cost | 작업 수행에 발생한 비용 |

여기서 주의할 점이 있다.

**Outcome과 Efficiency를 구분하여 측정한다는 것이 최종 평가에서 두 요소를 함께 고려하면 안 된다는 의미는 아니다.**

예를 들어 두 Agent의 문제 해결 정확성이 동일하다면 응답 속도가 빠르고 비용이 적게 발생하는 Agent를 선택하는 것이 합리적일 수 있다.

반대로 저렴하더라도 잘못된 답변을 자주 생성하는 Agent는 운영에 적합하지 않을 수 있다.

따라서 품질과 효율성을 독립적인 지표로 기록하되, 최종적인 판단에서는 서비스의 목적과 요구사항에 따라 함께 고려할 수 있다.

이러한 Outcome, Process, Efficiency는 평가를 이해하기 위한 실용적인 구분이며, 모든 Evaluation이 반드시 세 영역으로 나뉘어야 한다는 의미는 아니다.

## 3. 좋은 Evaluation을 설계하기 위한 원칙

Evaluation은 단순히 많은 테스트 케이스를 실행한다고 좋은 결과를 얻을 수 있는 것은 아니다.

평가 목적, 데이터, 평가 기준, 실행 조건이 적절하게 설계되어야 결과를 신뢰하고 활용할 수 있다.

### 3.1 성공 조건과 기대 행동을 정의해야 한다

Evaluation을 시작하려면 먼저 무엇을 성공으로 볼 것인지 정의해야 한다.

이 과정에서 등장하는 중요한 개념이 **Ground Truth**다.

Ground Truth는 평가 결과를 판단하기 위한 신뢰할 수 있는 기준 정보나 정답을 의미한다.

하지만 모든 Evaluation에서 하나의 정답 문장을 정의할 수 있는 것은 아니다.

예를 들어 다음과 같은 고객 지원 문의를 생각해 보자.

> "팀원을 초대하려는데 계속 실패합니다. 왜 그런가요?"

실제 데이터와 정책이 다음과 같다고 가정하자.

| 항목 | 값 |
|---|---|
| 문의자 역할 | `member` |
| 구독 | `pro`, `active` |
| 팀원 수 | 3명 |
| 팀원 제한 | 10명 |
| 초대 정책 | `owner/admin`만 가능 |

이 경우 정답에 해당하는 핵심 사실은 문의자에게 팀원 초대 권한이 없다는 것이다.

그러나 반드시 특정 문장을 그대로 출력해야 하는 것은 아니다.

"현재 계정은 팀원 초대 권한이 없습니다."와 "팀원 초대는 관리자 이상의 역할에서만 가능합니다."라는 설명은 표현이 다르지만 모두 관련된 사실을 전달할 수 있다.

평가를 위해 다음과 같은 기준을 정의할 수 있다.

- 원인을 권한 부족으로 식별했는가?
- 문의자의 역할과 초대 정책을 근거로 설명했는가?
- 구독 상태나 팀원 제한을 잘못된 원인으로 제시하지 않았는가?
- 적절한 후속 조치를 안내했는가?

이처럼 성공 조건을 정의할 때는 몇 가지 개념을 구분할 수 있다.

| 개념 | 의미 |
|---|---|
| Ground Truth | 정답을 판단하는 기준 사실 또는 검증된 정보 |
| Reference Answer | 평가에 참고할 수 있는 기대 응답 |
| Rubric | 결과를 어떤 기준으로 판단하고 점수화할지 정의한 규칙 |
| Success Criteria | 작업의 성공으로 인정하기 위한 조건 |

각각의 개념이 항상 모두 필요한 것은 아니다.

정답이 명확한 문제는 Code-based Evaluation으로 판단할 수 있고, 다양한 형태의 답변이 허용되는 문제는 Rubric을 중심으로 평가하는 것이 적절할 수 있다.

### 3.2 실제 사용 환경을 반영한 Dataset이 필요하다

Evaluation Dataset은 평가에 사용하는 입력과 기대 조건을 모아 놓은 데이터 집합이다.

각각의 평가 사례를 Test Case 또는 Task라고 부를 수 있다.

Dataset이 실제 사용 환경을 제대로 반영하지 못하면 평가 점수가 높더라도 운영 환경에서 비슷한 성능을 보장하기 어렵다.

예를 들어 고객 지원 Agent를 평가하면서 정상적인 결제 문의만 포함했다면, 권한 문제나 데이터 누락 상황에서의 성능은 알 수 없다.

따라서 Dataset에는 일반적인 상황뿐 아니라 실패 가능성이 높은 상황도 포함하는 것이 적절하다.

이때 사용할 수 있는 데이터의 출처는 다양하다.

- 실제 사용자 요청을 적절하게 처리한 데이터
- 도메인 전문가가 작성한 평가 사례
- 특정 실패 조건을 검증하기 위해 만든 합성 데이터
- 과거 장애나 실패 사례에서 수집한 데이터

대표적인 사례를 충분히 포함하는 것이 중요하지만, 단순히 실제 사용 빈도에 맞춘 데이터만 필요한 것은 아니다.

발생 빈도는 낮더라도 위험도가 높은 사례는 별도로 평가할 필요가 있다.

또한 기대 결과와 판단 기준을 함께 검증한 신뢰도 높은 평가 사례 집합을 **Golden Set**이라고 부르기도 한다.

Golden Set은 자동 평가 방법을 검증하거나, 시스템 변경 전후의 성능을 비교할 때 기준 데이터로 활용할 수 있다.

### 3.3 비교 가능한 실행 조건을 유지해야 한다

둘 이상의 Agent나 실행 방식을 비교하려면 통제할 수 있는 환경 차이를 줄여야 한다.

예를 들어 두 Agent의 성능을 비교할 때 입력 데이터가 다르거나, 서로 다른 정책 버전을 사용한다면 결과의 차이가 시스템 자체에서 발생한 것인지 판단하기 어렵다.

비교 목적에 따라 다음과 같은 조건을 통제할 수 있다.

- 평가 Dataset과 기대 결과
- Tool이 접근하는 데이터와 정책
- 실행 환경과 제한 조건
- 모델 및 시스템의 설정
- 측정 구간과 지표의 정의

모든 조건을 무조건 동일하게 만들어야 한다는 의미는 아니다.

예를 들어 서로 다른 모델을 사용하는 Agent를 비교하는 Evaluation이라면 모델 자체는 비교 대상이 되는 변수다.

중요한 것은 **어떤 차이를 비교하려는지 명확하게 정의하고, 나머지 차이가 결과에 미치는 영향을 최소화하는 것**이다.

### 3.4 반복 실행을 통해 신뢰성과 변동성을 확인해야 한다

LLM을 사용하는 Agent는 동일한 입력에 대해 항상 동일한 실행 결과를 보장하지 않는다.

같은 질문을 입력하더라도 답변의 표현이나 Tool 선택, 실행 경로가 달라질 수 있다.

이 때문에 한 번의 성공만으로 Agent가 안정적으로 작동한다고 판단하기 어렵다.

예를 들어 동일한 평가 사례를 다섯 번 실행했다고 가정하자.

| 실행 | 결과 |
|---|---|
| 1회 | 성공 |
| 2회 | 성공 |
| 3회 | 실패 |
| 4회 | 성공 |
| 5회 | 성공 |

이 경우 관측된 성공률은 80%다.

그러나 다섯 번의 실행만으로 실제 성공 확률이 정확히 80%라고 단정할 수는 없다. 평가 횟수가 적기 때문에 통계적인 불확실성이 크기 때문이다.

따라서 Evaluation에서는 평균적인 성능뿐 아니라 반복 실행에 따른 변동성과 실패 유형도 확인할 필요가 있다.

Anthropic의 *Demystifying Evals for AI Agents*에서는 이러한 특성을 설명하기 위해 `pass@k`와 `pass^k`를 소개한다.

- **pass@k**: k번의 시도 중 적어도 한 번 성공할 가능성
- **pass^k**: k번의 시도가 모두 성공할 가능성

두 지표는 서로 다른 질문에 답한다.

여러 번 시도해서 한 번이라도 정답을 찾으면 되는 작업이라면 `pass@k`가 의미 있을 수 있다.

반면 매번 안정적인 결과를 제공해야 하는 고객 대상 서비스라면 반복적인 성공 여부가 더 중요할 수 있다.

따라서 평가 횟수와 신뢰성 지표 역시 Agent의 사용 목적에 맞게 결정해야 한다.

## 4. 평가 결과는 어떻게 판단하는가?

평가 기준과 Dataset을 준비했다면 실제 결과를 어떻게 채점할지 결정해야 한다.

결과를 판단하는 구성 요소를 일반적으로 **Grader**라고 부른다.

대표적인 방법은 Code-based Grading, LLM-as-a-Judge, Human Evaluation으로 구분할 수 있다.

### 4.1 Code-based Grading

프로그램 코드와 명확한 조건을 이용해 결과를 검증하는 방법이다.

예를 들어 구조화된 출력의 필수 필드가 존재하는지 확인하거나, 실제 DB 상태가 기대 조건과 일치하는지 검증할 수 있다.

```python
assert result["status"] == "completed"
assert result["diagnosis_code"] == "permission_denied"
```

장점은 평가 결과가 비교적 명확하고, 빠르며, 반복하기 쉽다는 것이다.

반면 자연어의 의미나 설명 품질처럼 정답이 다양하게 표현될 수 있는 작업에서는 단순 문자열 비교만으로 충분하지 않을 수 있다.

따라서 명확한 사실이나 시스템 상태는 Code-based Grading으로 검증하고, 의미적 판단이 필요한 영역은 다른 평가 방법을 함께 활용할 수 있다.

### 4.2 LLM-as-a-Judge

LLM-as-a-Judge는 평가 대상과 별도로 LLM을 활용하여 결과의 품질을 판단하는 방법이다.

예를 들어 Agent가 생성한 답변이 문제의 원인을 올바르게 설명했는지, 제공된 근거에 부합하는지, 중요한 정보를 누락하지 않았는지 평가할 수 있다.

이때 평가 기준이 되는 Rubric을 명확하게 제공하는 것이 중요하다.

평가 방식에는 대표적으로 다음과 같은 형태가 있다.

- **Pointwise Scoring**: 개별 결과를 기준에 따라 채점
- **Pairwise Comparison**: 두 결과를 비교하여 더 적절한 결과 판단
- **Reference-based Evaluation**: 기준 답변이나 근거와 비교하여 평가

LLM-as-a-Judge는 자연어의 의미와 맥락을 비교적 유연하게 평가할 수 있다는 장점이 있다.

하지만 Judge 자체도 LLM이므로 평가가 항상 정확하거나 일관적이라고 보장할 수는 없다.

응답의 길이, 표현 방식, 비교 순서 등에 따라 편향이 발생할 수 있으며, 실제로 잘못된 판단을 내릴 수도 있다.

따라서 **LLM-as-a-Judge의 평가 결과 역시 검증 대상**이다.

평가 Rubric을 구체적으로 작성하고, 필요한 경우 Human Evaluation과 비교하여 판단의 일치도를 확인해야 한다.

또한 실제 Tool 실행 여부나 DB 상태와 같이 코드로 직접 확인할 수 있는 사실은 Judge의 추정에만 의존하지 않는 편이 적절하다.

### 4.3 Human Evaluation

Human Evaluation은 사람 또는 도메인 전문가가 직접 결과를 평가하는 방법이다.

특히 정답이 모호하거나 전문적인 판단이 필요한 작업에 적합하다.

예를 들어 고객에게 전달하는 답변이 충분히 이해하기 쉬운지, 정책적으로 적절한지, 복잡한 상황에서 필요한 정보를 빠뜨리지 않았는지 검토할 수 있다.

사람의 평가는 복잡한 맥락을 반영할 수 있지만 비용과 시간이 많이 들고, 평가자에 따라 판단이 달라질 수 있다는 한계도 존재한다.

따라서 평가 기준을 명확하게 제공하고, 여러 평가자의 판단을 비교하거나, 자동 평가 결과를 검증하는 용도로 활용할 수 있다.

세 가지 평가 방법은 서로 경쟁하는 관계가 아니다.

| 방법 | 적합한 평가 대상 | 주요 한계 |
|---|---|---|
| Code-based | 명확한 정답, 구조, 상태 검증 | 의미적 유연성 부족 |
| LLM-as-a-Judge | 자연어 품질, 복합적인 의미 판단 | 평가 편향과 변동성 |
| Human Evaluation | 전문적인 판단, 주관적 품질 | 시간과 비용, 평가자 간 차이 |

실제 Agent Evaluation에서는 평가 대상에 따라 이 방법들을 조합하는 것이 효과적이다.

## 5. Evaluation은 어떻게 활용되는가?

Evaluation의 가치는 평가 점수를 얻는 것만으로 완성되지 않는다.

평가 결과를 바탕으로 실패 원인을 분석하고, Agent를 개선하며, 변경 이후에도 품질이 유지되는지 확인할 수 있어야 한다.

### 5.1 Offline Evaluation과 Online Evaluation

Evaluation은 평가가 이루어지는 환경에 따라 Offline과 Online으로 구분할 수 있다.

**Offline Evaluation**은 미리 준비한 Dataset과 통제된 환경에서 Agent를 평가하는 방식이다.

새로운 Prompt나 모델, Tool 구성을 도입하기 전에 기존 시스템과 성능을 비교하거나, 알려진 실패 사례를 재검증하는 데 적합하다.

반면 **Online Evaluation**은 실제 운영 환경에서 발생하는 요청과 결과를 바탕으로 Agent를 평가하는 방식이다.

실제 사용자 피드백, 운영 지표, A/B Test 등을 활용할 수 있다.

두 방식은 목적과 한계가 다르다.

Offline Evaluation은 통제된 조건에서 비교하기 쉽지만, 운영 환경의 모든 상황을 재현하기 어렵다.

Online Evaluation은 실제 사용 환경을 반영하지만, 외부 조건의 영향을 받으며 실험 설계와 사용자 보호를 더욱 신중하게 고려해야 한다.

따라서 두 방식은 상호 보완적으로 활용할 수 있다.

### 5.2 Regression Evaluation

Regression Evaluation은 Agent의 변경으로 인해 기존에 정상적으로 수행하던 작업이 실패하지 않는지 확인하는 평가다.

예를 들어 Prompt를 수정하여 복잡한 고객 문의의 정확성을 개선했다고 가정하자.

새로운 문의에서 성능이 높아졌더라도 기존에 잘 처리하던 단순 문의에서 오류가 발생할 수 있다.

따라서 변경 전후의 성능을 비교하고, 이전에 성공했던 평가 사례를 반복 실행할 필요가 있다.

Regression Evaluation은 이러한 성능 저하를 발견하는 역할을 한다.

일반적인 소프트웨어의 Regression Test와 유사한 목적을 가지지만, Agent에서는 비결정성을 고려한 반복 평가와 허용 가능한 성능 변동 범위에 대한 판단이 필요할 수 있다.

### 5.3 Trace 기반 Failure Analysis

Evaluation 결과에서 실패 사례를 발견했다면 다음 질문은 왜 실패했는지다.

단순히 성공 여부만 기록하면 실패 원인을 파악하기 어렵다.

이때 활용할 수 있는 것이 **Trace**다.

Trace는 하나의 실행에서 발생한 모델 호출, Tool 호출, 중간 결과, 오류 등 실행 과정을 추적할 수 있도록 기록한 데이터다.

예를 들어 고객 지원 Agent가 잘못된 진단을 내렸다고 가정하자.

최종 답변만 확인하면 잘못된 진단이라는 사실은 알 수 있지만, 원인은 여러 가지일 수 있다.

- 필요한 Tool을 호출하지 않았을 수 있다.
- Tool이 잘못된 데이터를 반환했을 수 있다.
- 올바른 데이터를 받았지만 잘못 해석했을 수 있다.
- 실행 중 오류가 발생했지만 적절하게 처리하지 않았을 수 있다.

Trace를 분석하면 이러한 실패 지점을 구분하는 데 도움이 된다.

이때 실패 사례를 일정한 분류 체계로 정리하는 방법이 **Error Taxonomy**다.

예를 들어 Tool Selection Error, Data Interpretation Error, Policy Violation 등으로 실패 유형을 구분할 수 있다.

Error Taxonomy는 보편적으로 정해진 단일 분류표가 있는 것이 아니라, 시스템의 특성과 분석 목적에 따라 정의할 수 있다.

중요한 것은 실패를 단순히 하나의 점수로 처리하는 데 그치지 않고, 개선 가능한 원인으로 분해하는 것이다.

다만 Trace에 기록된 정보만으로 모든 실패 원인을 확정할 수 있는 것은 아니다. 필요한 정보가 누락되었다면 추가적인 테스트나 환경 검증이 필요할 수 있다.

### 5.4 Production Feedback Loop

Evaluation은 개발 단계에서 한 번 수행하고 끝나는 작업이 아니다.

운영 환경에서는 새로운 유형의 요청과 예상하지 못한 실패가 지속적으로 발생할 수 있다.

따라서 운영 과정에서 수집한 데이터를 다시 Evaluation에 반영하는 구조가 필요하다.

이러한 과정을 **Production Feedback Loop**라고 설명할 수 있다.

예를 들어 다음과 같은 흐름이다.

1. 운영 환경에서 실패 사례를 수집한다.
2. Trace와 사용자 피드백을 바탕으로 원인을 분석한다.
3. 재현 가능한 평가 사례를 작성한다.
4. 기존 Evaluation Dataset에 반영한다.
5. Agent 개선 후 다시 평가한다.

이 과정이 반복되면 Evaluation Dataset은 실제 운영 환경에서 발견된 문제를 반영하며 발전할 수 있다.

다만 운영 데이터를 평가에 활용할 때는 개인정보 보호, 민감정보 처리, 데이터 품질 등을 고려해야 한다.

## 6. Evaluation 결과를 Agent 설계 판단에 활용하기

지금까지 살펴본 Evaluation의 개념과 방법은 궁극적으로 시스템에 대한 판단을 지원하기 위한 것이다.

예를 들어 Agent의 Tool 사용 방식을 변경했다고 가정하자.

기존 Agent는 필요한 데이터를 순차적으로 조회하지만, 개선된 Agent는 서로 의존하지 않는 Tool을 병렬로 호출할 수 있도록 설계했다.

두 방식의 Evaluation 결과가 다음과 같다고 가정해 보자.

| 지표 | 기존 Agent | 개선된 Agent |
|---|---|---|
| 작업 성공률 | 90% | 90% |
| 평균 Latency | 4.8초 | 3.1초 |
| 평균 Token Usage | 8,900 | 8,700 |
| 정책 위반 건수 | 0건 | 0건 |

*위 수치는 설명을 위한 가상의 예시이며, 실제 평가 결과가 아니다.*

이 결과만 보면 개선된 Agent는 성공률을 유지하면서 응답 시간을 단축한 것으로 보인다.

그러나 이것만으로 모든 상황에서 개선된 Agent가 더 낫다고 단정할 수는 없다.

예를 들어 병렬 Tool 호출이 특정 오류 상황에서 실패율을 증가시키는지, 더 많은 동시 요청이 발생하는 운영 환경에서도 같은 효과가 유지되는지 확인할 필요가 있다.

또한 평균 Latency가 줄어들었더라도 일부 요청의 지연 시간이 크게 증가했다면 평균값만으로는 이러한 특성을 파악하기 어렵다.

따라서 필요에 따라 Latency의 분포나 실패 유형 등을 추가로 분석할 수 있다.

이처럼 Evaluation은 변경 전후의 수치를 비교하는 것에서 나아가, **어떤 조건에서 어떤 설계가 적절한지 판단하기 위한 근거**를 제공한다.

같은 원리는 서로 다른 모델을 사용하는 Agent, Tool 구성의 변경, Workflow와 Agent의 비교 등 다양한 설계 문제에도 적용할 수 있다.

중요한 것은 Evaluation이 특정 아키텍처의 우수성을 증명하기 위한 수단이 아니라는 점이다.

Evaluation은 시스템의 실제 특성을 확인하고, 요구사항과 제약 조건에 적합한 선택을 내리기 위한 근거를 마련하는 과정이다.

## 마치며

Agent Evaluation은 최종 답변에 단순히 점수를 부여하는 작업이 아니다.

먼저 평가 목적과 성공 조건을 정의하고, 이를 검증할 수 있는 Dataset과 평가 기준을 마련해야 한다.

이후 적절한 Grader를 활용하여 결과와 실행 과정을 평가하고, 반복 실행을 통해 신뢰성과 변동성을 확인할 수 있다.

또한 평가 결과에서 발견된 실패를 분석하고, 운영 환경의 피드백을 반영하면서 Evaluation을 지속적으로 개선해야 한다.

모든 Agent에 공통으로 적용할 수 있는 하나의 완벽한 평가 지표는 존재하지 않는다.

어떤 Agent에서는 답변의 정확성이 가장 중요하고, 다른 Agent에서는 작업 성공 여부나 안전성, 응답 시간이 중요한 조건이 될 수 있다.

따라서 Evaluation을 설계할 때 중요한 것은 많은 지표를 수집하는 것이 아니라, **Agent가 해결하려는 문제에 맞는 평가 기준을 정의하고 그 결과를 실제 의사결정에 활용할 수 있도록 만드는 것**이다.
